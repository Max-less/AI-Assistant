# Оценка качества RAG-пайплайна

Главный артефакт — **таблица «до/после»** ниже: как меняются метрики при изменении
одного параметра за итерацию. Таблица собирается автоматически из
`data/eval_results_*.json` скриптом `scripts/compare_eval.py`.

> **Статус прогонов.** Все метрики получены на реальных прогонах против живого
> GigaChat (24 вопроса). Логика метрик дополнительно покрыта офлайн-тестами
> `tests/test_evaluator.py` (15 passed, без сети). Итерации ретривера прогонялись
> в режиме `--retrieval-only` (быстро, без LLM), полный пайплайн — обычными
> прогонами. Числа GigaChat недетерминированы — небольшие колебания между
> повторами одной конфигурации возможны.

## Что измеряем

| Метрика | Функция (`src/evaluator.py`) | Что показывает |
|---|---|---|
| **recall@k** | `eval_retrieval` | Попал ли ожидаемый источник (`expected_source`) в top-k извлечённых чанков. Считается только по вопросам из базы. Сопоставление по **имени файла** (в индексе `source` — это полный путь). |
| **keyword_recall** | `eval_answer_keywords` | Средняя доля ожидаемых ключевых слов, встретившихся в ответе (регистронезависимо). Дополнительно: `all` (все слова) и `any` (хотя бы одно). |
| **faithfulness** | `eval_faithfulness_llm` | LLM-as-a-judge отдельным промптом отвечает 1/0: «следует ли ответ строго из контекста». Честный отказ и пустой контекст засчитываются как 1 (факты не выдуманы). |
| **refusal_rate** | `eval_honest_refusal` | Доля вопросов **вне базы**, на которые система честно ответила «нет информации». Проверяет честное «не знаю». |

## Набор вопросов

`tests/eval_questions.json` — **24 вопроса**: 20 из базы (Scrum, ГОСТ 19.201-78 ТЗ,
Agile-оценка, DevOps, управление проектами) + **4 вне базы** (столица Австралии,
рецепт борща, автор «Войны и мира», число планет) для проверки честного отказа.

Схема элемента:
```json
{
  "id": "q01",
  "question": "Какие роли есть в Scrum?",
  "expected_source": "2020-Scrum-Guide-Russian.pdf",
  "expected_keywords": [
    ["Владелец продукта", "Product Owner"],
    ["Scrum-мастер", "Scrum Master"],
    ["Разработчики", "Developers"]
  ],
  "in_base": true
}
```
- `expected_source` — имя файла, либо **список** допустимых имён (для тем, покрытых
  несколькими документами, напр. DevOps / управление проектами), либо `null` для
  вопросов вне базы.
- Каждое ожидаемое «ключевое слово» — это **группа синонимов** (RU/EN-варианты,
  словоформы); засчитывается, если в ответе найден любой вариант. Это важно,
  потому что GigaChat часто отвечает английскими Scrum/DevOps-терминами
  (Product Owner, Sprint Backlog, Continuous Delivery), хотя источник — русский.
  Допускается и простая строка вместо группы.

> Примечание: имя `scrum_guide_2020.pdf` из исходного примера задания в базе
> отсутствует — реальный файл называется `2020-Scrum-Guide-Russian.pdf`. Все
> вопросы привязаны к **фактическим** файлам из `knowledge_base/`. Два английских
> DevOps-PDF не попали в индекс (нет извлекаемого текста) и как источники не используются.

## Как запустить

```bash
cd rag_service            # активировать venv
# офлайн-проверка логики метрик (без сети/GigaChat):
python -m pytest tests/test_evaluator.py -q

# только recall@k — без GigaChat и без ключа (быстро):
python scripts/run_eval.py --label baseline --alpha 1.0 --no-reranker --retrieval-only

# полный прогон (нужен действующий GigaChat-ключ; расходует квоту):
python scripts/run_eval.py --label baseline_full --alpha 1.0 --no-reranker --no-expander

# собрать таблицу «до/после» из всех прогонов в этот файл:
python scripts/compare_eval.py
```

Полный `run_eval.py` обращается к живому GigaChat (расходует квоту); при первом
запуске скачиваются модели эмбеддера и реранкера (сейчас обе уже в кэше HF).
Режим `--retrieval-only` считает только recall@k и не требует ключа/сети.

## Итерации (по одному изменению за шаг)

**A. Ретривер** (`--retrieval-only`, без LLM — быстро, фокус на recall@k):

| # | Label | Что меняем относительно предыдущего | Гипотеза |
|---|-------|-------------------------------------|----------|
| 0 | `baseline` | только dense (`alpha=1.0`), без реранкера, `thr=0.5` | точка отсчёта |
| 1 | `hybrid` | `alpha=1.0→0.5` (добавили BM25) | recall@k ↑ |
| 2 | `rerank` | включили cross-encoder реранкер | recall@k ↑ (переранжирование пула) |
| 3 | `rerank_thr0.7` | `thr=0.5→0.7` (строже гейт релевантности) | больше отказов вне базы ↔ риск потерять recall |

**B. Полный пайплайн** (живой GigaChat — качество ответа):

| Label | Что меняем относительно `baseline_full` | Гипотеза |
|-------|------------------------------------------|----------|
| `baseline_full` | dense, `top_k=5`, базовый промпт | точка отсчёта |
| `topk8_full` | `top_k=5→8` (больше контекста в промпт) | keyword_recall ↑ |
| `strict_full` | базовый промпт → `strict` | faithfulness/refusal ↑ |
| `rerank_full` | `alpha=0.5` + реранкер (продакшн-ретривер) | держит качество |

Команды каждой строки — в шапке `scripts/run_eval.py`. `recall@1/3/5` считаются
при извлечении top-5, поэтому `top_k` (число чанков в промпт) влияет на качество
ответа, но не на recall@k≤5. После прогонов `python scripts/compare_eval.py`
пересобирает таблицы ниже.

## Выводы по итерациям (recall@k — реальные прогоны)

1. **Dense-базлайн силён сам по себе:** recall@5 = 0.95, recall@1 = 0.85.
2. **BM25-гибрид ухудшил результат:** `alpha 1.0→0.5` уронил recall@5 0.95 → 0.85.
   Лексический сигнал BM25 на этом корпусе добавляет шум (много похожих по словам
   фрагментов в учебниках по УП), а не пользу. Вывод: «гибрид» — не всегда лучше,
   слепо включать BM25 не стоит.
3. **Реранкер компенсирует шум гибрида:** cross-encoder на пуле кандидатов вернул
   recall@5 обратно к 0.95 (0.85/0.90/0.95). То есть совместное переранжирование
   (query, chunk) исправляет ошибки RRF-слияния и возвращает качество dense-базлайна.
   Стоимость — заметно дольше на CPU (≈14–20 c/вопрос даже при пуле 8).
4. **Порог релевантности не отсекает вопросы вне базы:** `thr 0.5→0.7` не изменил
   ни recall, ни `empty_retrieval_rate` вне базы (0.0 в обоих случаях). Косинус e5
   остаётся высоким даже для офтопика («столица Австралии» и т.п.), поэтому гейт по
   косинусу на этом корпусе их не разделяет (≤0.7). Честный отказ должен
   обеспечиваться **промптом** (вариант `strict`), а не порогом; дальнейшее
   повышение порога рискует отсекать валидные вопросы из базы.

### Качество ответа (полный пайплайн)

5. **Faithfulness и честный отказ — на потолке уже у базлайна:** `faithfulness = 1.0`
   и `refusal_rate = 1.0` (все 4 вопроса вне базы корректно отклонены) у всех
   dense-конфигов; у продакшн-конфига с реранкером — `0.958` (один ответ из 24
   судья счёл недостаточно обоснованным — в пределах недетерминизма GigaChat).
   `top_k 5→8` и строгий промпт эти метрики не меняют — система и так не выдумывает
   факты и честно отказывается. То есть основной рычаг качества здесь —
   **извлечение** (раздел A), а генерация уже надёжна.
6. **Метрику ключевых слов пришлось чинить, а не пайплайн:** первый прогон дал
   `keyword_recall ≈ 0.28`, потому что GigaChat отвечает английскими терминами
   (Product Owner, Sprint Backlog, Continuous Delivery), а ключи были русские.
   После перевода ключей в **группы синонимов RU/EN** стало `≈ 0.97` при тех же
   ответах. Вывод: подстрочная keyword-метрика чувствительна к формулировкам —
   её надо валидировать на реальных ответах (faithfulness-судья здесь устойчивее).

**Рекомендация:** основной рычаг — извлечение (dense + cross-encoder реранкер;
BM25 на этом корпусе скорее мешает). Генерация уже faithful и честно отказывается,
поэтому усилия стоит вкладывать в ретривер и в поддержание строгого промпта для
отказов, а не в косинусный гейт (он офтоп не отсекает).

## Замечания / ограничения

- `keyword_recall` основан на подстроках → чувствителен к формулировкам; смягчён
  группами синонимов (RU/EN) и подсчётом как **мягкой средней доли**, а не
  «всё-или-ничего». Для качества ответа надёжнее опираться на faithfulness-судью.
- Контекст для судьи faithfulness извлекается отдельно от `pipeline.answer()`;
  при включённом экспандере (LLM) возможна лёгкая недетерминированность — в
  итерациях экспандер по умолчанию выключен.
- Ответы GigaChat недетерминированы: небольшие колебания метрик между прогонами
  одной и той же конфигурации — норма.
